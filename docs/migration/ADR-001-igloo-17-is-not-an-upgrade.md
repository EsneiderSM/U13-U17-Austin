# ADR-001 · Igloo 17 is not an upgrade of Igloo 13: remove Igloo and keep the site's own content model

- **Status:** accepted (2026-11-12)
- **Decision:** option 1, *remove the Igloo package and keep the current content model as site-owned code*. The plan is rebuilt from phase P3.
- **Pending confirmation:** LittleNorth (vendor), see "Open items".

## Context

The site (Austin Opera, Umbraco 13) is built on the **Igloo** theme by LittleNorth:
`LittleNorth.Igloo` 13.1.5 + `LittleNorth.Igloo.Core` 13.1.5, with views customised by Adage.

The first migration plan (plan v1, generated by the analysis on 2026-11-12) assumed that
`LittleNorth.Igloo` **17.4.2** was the Umbraco 17 version of the same theme:

- P3 replaced Igloo 13.1.5 with Igloo 17.4.2 and removed Igloo.Core (it has no v17 build).
- P5 was going to upgrade the database copy, letting each package run its own migrations.

## Evidence (decompiled `LittleNorth.Igloo` 17.4.2 and `LittleNorth.Igloo.Core` 13.4.0)

1. **Igloo 17's migration plan starts from an empty state.** `Igloo.Migrations.IglooPackageMigrationPlan`
   is one linear chain: `CleanInstallPackageMigration` → `PackageMigration17_1_1` → … → `PackageMigration17_4_2DisqusGroupKey`.
   It contains **no Igloo 13 state** and no "from" branch, so an existing Igloo 13 database cannot enter it
   (`MigrationPlan.ThrowOnUnknownInitialState`).
2. The only GUID shared by both versions, `0cc0eba1-9960-42c9-bf9b-60e150b429ae`, is **not** a migration
   state. It is the key of a data type (`TypographySchemaInstaller.FontFamilyDataTypeKey` /
   `TextstringDataTypeKey`).
3. **The clean install imports a complete package**, an embedded `package.xml` ("Igloo 17.1.0") with
   81 document types, 58 data types, 7 templates, 4 dictionary items and **a demo content tree** ("Site").
4. **The content model is incompatible.** Comparison with `AustinOpera_U13_Stage_u17`:

   | | Igloo 17 package | This site (Igloo 13) |
   |---|---|---|
   | Document types | 81 | 119 |
   | Same key | **0** | |
   | Same alias, different key (would collide) | 11: `site`, `sitemap`, `page`, `settings`, `general`, `globalContent`, `globalContentHolder`, `accordionItem`, `sectionNavigationItem`, `bigNavigationItem`, `navigationItem` | |
   | Block types | `accordionBlock`, `heroBlock`, `sectionBlock`, `podBlock`, `sliderBlock`… | `columnAccordion`, `hero`, `grid`, `gallery`, `footerContact`, `columnCard`… |
   | Data types with the same key | **0 of 58** | 108 in total |

   Igloo 17 ships nothing that converts Igloo 13 blocks or content.
5. The package readme does not mention upgrading from Igloo 13.

**Conclusion:** Igloo 17 is a new product for the new backoffice, not version 17 of the theme this site
uses. There is no supported upgrade path. Forcing the migration state (for example to the clean install
state) would install Igloo 17's schema and demo content next to the site's own, with alias collisions,
and would migrate none of the 201 pages.

## Options considered

1. **Remove Igloo and keep the current content model as site-owned code (chosen).**
   Document types, data types and content already live in the database and stay as they are. The views
   (Igloo views customised by Adage) become the site's own code. The work is:
   - replace what `Igloo.Core` provided: the surface controllers (contact form, newsletter, login,
     register), `ISettingsService`, extensions and models used by the views;
   - replace Igloo's AngularJS property editors (ButtonsButtonsButtons, ColorValue, IglooMeasurmentValue,
     IglooApprovedColorPicker, IconPicker, IglooDashboard, see risk R-002) with core editors or with
     site-owned extensions for the new backoffice, keeping the stored values readable;
   - leave the `Umbraco.Core.Upgrader.State+Igloo` key alone: without the Igloo package no plan reads it.
     It can be deleted after go-live.

   *For:* no content migration, the site keeps its look and markup, and there is no dependency on the vendor
   or its licence for v17. *Against:* the theme code becomes ours to maintain.
2. **Adopt Igloo 17 for real.** This means a redesign and a content migration: map each Igloo 13 block to
   an Igloo 17 block, migrate the 201 documents, and accept a different front end. Much more expensive and
   risky, and the outcome is a different site.
3. **Wait for LittleNorth** before deciding. This was not chosen as a blocker, but their confirmation is
   requested (see below).

## Consequences

- **Plan v1 is superseded from P3 on.** P1 and P2 stay accepted. P3–P5 were rolled back (code and
  database copy), and the plan is regenerated from P3 with this decision as input (plan v2).
- The P3 work that does not depend on Igloo still applies: .NET 10, Umbraco 17.8.1, Forms 17 (now a direct
  reference), Skybrud Redirects 17, uSync 17, Azure Blob 17, Smidge removal, Models Builder
  regeneration.
- **Upgrading Igloo to 13.4.0 is no longer needed.** It may still be useful if any Igloo 13.4 data fix
  matters for the content. The plan decides.
- Risks R-001 (Igloo/Igloo.Core) and R-002 (Igloo AngularJS editors) are now addressed by *removal and
  replacement*, not by upgrading.
- **Known DB state of the copy:** P2's manual clean-up (deleting legacy data types 1048/1049) was
  accidentally applied to the original database, not to the copy, and was undone by the restore. It still
  has to be done on the copy, either in the Umbraco 13 backoffice before the database upgrade or in the
  Umbraco 17 backoffice after it.

## Resulting plan (v2, generated 2026-11-12 from this record)

P1–P2 are unchanged (done). The new phases are listed below. Effort for the whole plan is 206 h, versus 188 h in v1.

| Phase | Title | Hours |
|---|---|---|
| P3 | Replace the Igloo engine with the site's own code (still on Umbraco 13) | 30 |
| P4 | Remove the Igloo packages (still on Umbraco 13); delete data types 1048/1049 on the copy | 8 |
| P5 | Move theme and SEO settings to standard Umbraco editors (still on Umbraco 13) | 14 |
| P6 | Move the code to .NET 10 and the Umbraco 17 packages | 14 |
| P7 | Upgrade the database copy to Umbraco 17 (unattended, on a fresh restore) | 10 |
| P8 | Get every page rendering on Umbraco 17 | 30 |
| P9 | Forms and member login on Umbraco 17 | 14 |
| P10 | Front-end assets on supported tools | 10 |
| P11 | Backoffice editing experience on Umbraco 17 | 12 |
| P12 | Full verification, final rehearsal and go-live runbook | 28 |

Key idea: everything that depends on Igloo is replaced and removed **while the site is still on Umbraco 13**
(P3–P5), where it can be compared page by page against the running site. Only then does the site move to 17.

The plan files are in the migration job: `plan.json` (v1, superseded), `plan.v2.json` (current) and
`decision.v2.md` (this record as submitted). The P3–P5 attempts made under v1 are archived in the job state.
For P3, the decompiled `LittleNorth.Igloo.Core` 13.1.5 is in the job's
`reference/igloo-core-13.1.5-decompiled/` folder. It is reference material only and is not part of the site.
